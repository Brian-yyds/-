# 服务器监控保护

服务器只运行GMGN、Web3与特级警报；本机合约监控、快讯和跟单保持独立。服务器使用自己的GMGN Key及Telegram配置，SFTP保持暂停。

## 与本机一致的核心

采集、阈值、固定10日匹配池、不可撤销的合格事件、每日去重、持久收件队列、数据库连接、完整性巡检、进程监督和声音去重使用同一套源码。服务器专用页面及启动器位于deploy/server_app.py、deploy/server_launch.py，只启动三个原有进程。

GMGN报警后与已收到的有效Web3事件按链和CA双向匹配，先后顺序都支持；GMGN后续成交额回落不撤销合格记录。市值缓存与报警原始快照分开。声音读取已发送到当前警报框的相同记录，只对新GMGN事件发声。

## 独立保护

- perp-recovery.timer每30秒检查进程、来源请求进度、心跳、特级快照、待入库队列及推送状态。没有新警报不等于故障。
- 保留错误文字但请求不再前进、缺失某一条链、持久收件队列超过180秒仍未处理，都作为实际停滞处理。正常限频等待、持续重试和主动暂停不会被当成卡死。
- 存活但卡住的服务需连续两次、间隔至少25秒确认后才恢复；每个服务每小时最多3次，恢复动作至少间隔5分钟。进程退出另由原监督器及systemd恢复。启动有宽限，不能将30秒检查周期误解成所有故障一定30秒内修好。
- 当前文件每30秒与server-standard-manifest.json中的批准版本哈希核对。发现漂移只报告异常，不自动拉取未经验证的新代码。
- perp-maintenance.timer每小时对监控库与Telegram记录库进行完整integrity_check；发现损坏或磁盘空间危险时明确报告，不清库、不自动用旧备份覆盖当前数据、不通过循环重启掩盖问题。
- 每天分别备份两份数据库，使用SQLite一致性备份、校验后改名，各保留最近7个日期；已有当天备份也会复检，文件存在不代表健康。
- 本项目三个运行日志按logrotate轮转，避免长期运行耗尽磁盘。

运行状态写入/opt/perp-workbench/shared/recovery/status.json和shared/maintenance/status.json。服务器页面的“规则与运行状态”展示版本、异常、巡检与备份结果。巡检不调用GMGN或律动，不消耗它们的额度。

## 更新方法

GitHub保存不等于服务器部署。构建源代码白名单包使用deploy/build_server_standard.py，严禁打包user_data、密钥、日志或本机数据库。服务器先在新的、非当前发布目录运行相关测试，再由deploy/install_server_standard.py备份状态、校验文件、切换发布目录并重启本项目服务。

安装器保留固定服务的崩溃启动限额。计划部署前仅清一次systemd启动计数，避免多个验证切换触发启动上限；不会重置接口退避、报警去重或恢复脚本的每小时限额。安装校验失败会切回旧版本。不要直接覆盖正在运行的发布目录。

每日备份路径为/opt/perp-workbench/shared/backups；安装前备份位于shared/standard-upgrade-backup-*。备份含报警数据和推送去重记录，保持私有，不上传GitHub。

需要主动维护或停机时，先停止恢复和维护定时器，并停掉相应一次性检查服务，避免保护机制将其误认为意外停止；来源暂停仍通过服务器页面单独保存。

## 完整性边界

已收到并成功写入持久收件队列的合格事件可以重放和去重。Web3 SOL接口存在分页重复，来源未返回的信号不能凭空补齐；页面明确显示覆盖有限。独立网络和Key也意味着本机与服务器不一定同秒触发。

Telegram发送若网络中断且结果不确定，记录为uncertain，避免盲目重发造成重复；该状态需要核对，不能声称绝对不漏或绝不重复。当前程序和保护可发现、恢复多类故障，但不保证第三方接口永远可用。
